      Documentation

      How this system works

      An invoice arrives as a PDF and somebody has to decide whether to pay it, and say why. This is what happens in between.

      The model reads. The code decides. Nothing here asks a model what to do.

      1. The problem

      Before an invoice can be paid, three questions have to be answered, and no single document answers any of them: are we allowed to pay this supplier, did we order this, and have we paid it already? Each is settled against a different record held somewhere else.

      Three answers, not two

      Approve All nine checks passed. Nothing here needs a person.
      Flag The work is done and something still needs a human eye.
      Reject Something reviewing will not fix — an unapproved supplier, a duplicate, a budget already spent.

      2. The seven steps

      Every invoice takes the same seven steps, in the same order. Watch them happen on the page — each one says what it is doing, then what it found.

      A failure is then attributable to one step rather than to “the system”.

      3. Reading the page

      Step 2 is the only one that uses a model, and it is asked exactly one thing: report what is printed on this page — the supplier, the dates, the amounts, the purchase order it names — and for every figure, the words it was read from.

      Step 3 looks those words up in the document's own text. A figure whose words are found is one the system checked; a figure whose words are not is one it only has a claim about.

      4. What it checks against

      Each of the nine checks holds the invoice against one specific record.

      All nine are listed, with the live number each uses, on the page. Change the purchase-order tolerance from 2% to 10%, re-run the same invoice, and the answer changes from flagged to approved — a round trip a test asserts.

      Why the worst result wins

      The decision is the most serious failure among the nine results — a pure function of them, so the same invoice and the same reference data always give the same answer. Nothing is averaged or weighted.

      5. What gets written down

      Each step writes its own row as it happens — what it did, how long it took, what it produced. Those rows are what the interface renders.

      The ledger is what makes this stateful. An approved invoice books what it spent against its purchase order, so the next invoice is judged against a budget this one already moved — the split-invoice case, where only the running total sees the problem.

      6. Raising a purchase order yourself

      The other half of the loop: the system can write an invoice against a purchase order you raise and put it through the same seven steps.

      What you raise goes into the same table the pipeline matches against, tagged as yours so it is never confused with the seeded demo data. The invoice it writes is a real PDF with real text on the page, submitted the way a dragged-in file is — the pipeline is not told where it came from.

      Each of the three states the verdict it should earn before it runs, and the run view shows that beside what the rules decided.

      7. What it deliberately does not do

      Real limits on what is being shown, stated rather than left to be discovered.

      • Invoices arrive as a file, not by email. Email intake is a listener in front of step 1 — no logic, so it is out of scope.
      • The vendor and purchase-order lists stand in for a procurement system. The seam where a real one would plug in is real; the data behind it is invented.
      • Everything is in rupees, one entity, one tax regime. Multi-currency would change every threshold comparison.
      • Offline mode proves the deterministic half, not reading quality. Its fixtures are the true values of the samples, not recorded model output.
      • The thresholds are plausible mid-market values, not policy. A real deployment would replace every one, which is why they are editable.
